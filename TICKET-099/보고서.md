### A1. 패킷이 두 번에 나뉘어 도착하면 서버가 죽는다

**재현 방법**

1. 서버를 새로 띄운다. 서버 창에 `[TCP] 포트 13582번에서 접속을 기다립니다` 가 뜬 것을 확인한다.
2. LoadTester에서 `2` 를 누른다. 본문 55바이트를 27바이트와 28바이트로 쪼개 50ms 간격으로 보내고, 이어서 정상 패킷을 하나 더 보낸다.
3. 서버 창과 LoadTester 창을 본다.

**기대** 두 조각을 합쳐 채팅 1개로 처리하고, 이어서 보낸 정상 패킷도 돌려준다.

**실제** 서버 창에 아래 예외가 찍히고 서버가 종료됐다.
```
Unhandled exception. Newtonsoft.Json.JsonReaderException: Unterminated string.
Expected delimiter: ". Path 'Message', line 1, position 55.
   at BattleArena.ClientSession.HandlePacket(String json) in …\ClientSession.cs:line 70
   at System.Threading.Tasks.Task.<>c.<ThrowAsync>…
```
LoadTester에는 `→ 전송 실패 : 현재 연결은 원격 호스트에 의해 강제로 끊겼습니다.` 와 `(아무것도 안 돌아왔습니다)` 가 나왔다.

**증거**

- before: `증거/A1_before_split_1028_000140.png`, `증거/logs/server_1028_000026.log`
- after: `증거/A1_after_split_1028_002119.png`, `증거/logs/server_1028_002101.log`. `{"Type":12,…,"Message":"AAAA-분할전송-테스트-BBBB"}` 와 `{"Type":12,…,"Message":"정상패킷-그다음"}` 가 둘 다 돌아왔다.
- after 캡처에서는 통계 줄이 t=4s에서 멈춰 있다. 찍기 전에 서버 콘솔 창을 클릭했는데, 그때 창이 '선택' 모드로 바뀌면서 출력이 잠깐 멈춘 것이다. 서버가 죽은 것은 아니다. 원본은 첫 메시지에서 죽었는데 after는 두 메시지를 다 돌려줬다.

![A1 before](증거/A1_before_split_1028_000140.png)
![A1 after](증거/A1_after_split_1028_002119.png)

**원인** `OutsourcedServer/PacketHelper.cs` L51, L63

받은 바이트 수(반환값)를 확인하지 않고 딱 한 번만 읽는다. (A2도 같은 줄이지만 원인이 다르다. A2는 "기다리는 방식"이 문제다.)

TCP는 경계가 없는 스트림이라서 `Receive(buf, 0, size)` 는 요청한 만큼이 아니라 지금 도착해 있는 만큼만 돌려준다. 그런데 L63은 반환값을 버리고 다시 읽지 않는다. 그래서 본문이 27바이트만 와 있을 때 나머지 28바이트가 0으로 채워진 버퍼를 그대로 JSON으로 읽고, 55번째 글자에서 `Unterminated string` 예외가 난다. 뒤늦게 도착한 28바이트는 다음 패킷의 헤더로 잘못 읽힌다. 헤더를 읽는 L51도 4바이트를 다 받았는지 확인하지 않는다.

**수업 근거**

- 3주차 9쪽: TCP는 "스트림"이라 메시지가 붙어서 오기도 하고, "반대로 잘려서 올 수도 있습니다".
- 3주차 10쪽: "먼저 4바이트를 읽는다 → 그 다음 정확히 30바이트를 읽는다". 이렇게 하면 "붙어 와도 잘려 와도 정확히 나눌 수 있습니다".
- 5주차 실습 코드 PacketHelper.cs의 `ReceiveExactAsync` 는 `while (received < count)` 로 다 받을 때까지 반복해서 읽는다. 납품본에는 이 반복이 없다.

**고친 코드**
```csharp
// before (L51, L63)
int n = await Task.Run(() => socket.Receive(header, 0, 4, SocketFlags.None));
...
await Task.Run(() => socket.Receive(body, 0, bodyLength, SocketFlags.None));

// after: 요청한 바이트를 다 받을 때까지 반복
if (!await ReadExactAsync(socket, header, 4)) return null;   // 상대가 연결을 닫음
...
if (!await ReadExactAsync(socket, body, bodyLength)) return null;

private static async Task<bool> ReadExactAsync(Socket socket, byte[] buffer, int size)
{
    int read = 0;
    while (read < size)
    {
        int n = await Task.Run(() => socket.Receive(buffer, read, size - read, SocketFlags.None));
        if (n == 0) return false;   // 상대가 연결을 닫음
        read += n;
    }
    return true;
}
```
이 단계에서는 블로킹 `Receive` 를 일부러 그대로 두었다. 부분 수신과 부하 문제를 따로 고쳐서, 각각 고쳤을 때 숫자가 어떻게 바뀌는지 보려고 했다 (Part B 측정 ②).

### A2. 동시 접속 50명부터 로그인이 대부분 실패한다

**재현 방법**

1. 서버를 새로 띄운다.
2. LoadTester에서 `1` 을 누르고 그냥 엔터를 친다. 10·50·100·300·500명 순서로 돌고, 봇마다 접속 → 로그인 → WELCOME을 최대 10초 기다린다.
3. CSV의 성공/실패, 그리고 서버 통계 줄의 `접속` 과 `스레드` 를 본다.

**기대** 500명까지 대부분 성공하고, 사람이 늘수록 지연이 조금씩 늘어난다.

**실제** CSV 2026-10-27 23:48:58~23:49:48 행: 10명 10/0, 50명 19/31, 100명 22/78, 300명 28/272, 500명 44/456. 50명부터 p95 지연이 9,914ms로 LoadTester의 10초 한도에 붙는다. 같은 시간 서버 통계 줄은 `접속 14 | 스레드 15` → `접속 22 | 스레드 26` → `접속 41 | 스레드 42` → `접속 62 | 스레드 63` 이었다. 약 50초 동안 스레드가 12개에서 63개로, 1초에 하나 정도씩 늘었다 (`증거/logs/server_1027_233628.log` t=751~800s).

**증거**

- before: `측정결과_22220676.csv` 23:48:58~23:49:48 행, `증거/B1_before_load_결과_1027_235137.png`, 서버 로그 `증거/logs/server_1027_233628.log`
- 중간 (A1만 고친 뒤): 같은 CSV 2026-10-28 00:21:50~00:22:41 행, `증거/B2_mid_load_결과_1028_002253.png`, 서버 로그 `증거/logs/server_1028_002139.log` (서버 스레드 최고 83)
- after: 같은 CSV 2026-10-28 00:25:39~00:25:50 행, `증거/B3_after_load_진행_1028_002549.png`, `증거/B3_after_load_결과_1028_002559.png`, 서버 로그 `증거/logs/server_1028_002522.log`. 50명 50/0, 100명 100/0, 300명 299/1, 500명 499/1이었고 서버 스레드는 최고 32개였다.

![B1 결과](증거/B1_before_load_결과_1027_235137.png)
![B3 결과](증거/B3_after_load_결과_1028_002559.png)

**원인** `OutsourcedServer/PacketHelper.cs` L51, L63

`Task.Run` 으로 감싼 블로킹 `Receive` 로 다음 패킷을 기다린다. (A1은 같은 줄에서 "반환값을 안 보는" 문제였다. A1만 고친 측정 ②에서도 부하 결과는 그대로였다.)

`Task.Run(() => socket.Receive(...))` 는 겉으로는 await를 쓰지만, 실제로는 스레드풀 스레드 하나가 데이터가 올 때까지 `Receive` 안에서 멈춰 있다. 로그인한 접속자는 다음 패킷을 기다리는 내내 스레드 하나를 붙잡고 있으니, 접속자 수가 곧 묶인 스레드 수가 된다. 통계 줄의 `접속 22 | 스레드 26`, `접속 62 | 스레드 63` 이 그 모습이다. 내 PC는 스레드풀이 처음에 바로 내주는 스레드가 12개(LoadTester 8번 "스레드풀 최소 : 워커 12")이고, 그 뒤로는 위 로그처럼 1초에 하나 정도씩만 늘어난다. 그래서 12명을 넘으면 새 접속 받기, LOGIN 처리, WELCOME 보내기 같은 일이 빈 스레드를 기다리며 줄을 선다. 자세한 숫자는 Part B에 정리했다.

**수업 근거**

- 4주차 16쪽 "흔한 실수: 네트워크 대기를 Task.Run 으로 감싸는 것 → 대기 중에는 CPU를 안 쓰는데, 쓰레드만 하나 더 잡아먹습니다 → 오히려 손해입니다". 납품본 L50 주석 "Receive는 블로킹 함수라서 Task.Run으로 감싸 비동기화했습니다"가 이 실수에 해당한다.
- 4주차 7쪽: 쓰레드 하나는 한 번에 한 가지 일만 하고, 그래서 "1명당 1쓰레드" 방식은 불가능하다.
- 4주차 8쪽 (C10K): 해결 방법은 "기다리는 동안 쓰레드를 놀리지 말자"이고, 그러면 "쓰레드 몇 개로 충분합니다".
- 4주차 11쪽: await는 "결과가 올 때까지 멈춘다. 단, 쓰레드는 반납한다."
- 4주차 19쪽: PacketHelper.cs의 "Receive → ReceiveAsync". 4·5주차 실습 코드도 `await socket.ReceiveAsync(...)` 를 쓴다.

**고친 코드**
```csharp
// before (A1을 고친 뒤의 ReadExactAsync 안)
int n = await Task.Run(() => socket.Receive(buffer, read, size - read, SocketFlags.None));

// after: 기다리는 동안 스레드를 돌려주는 비동기 수신
int n = await socket.ReceiveAsync(
    new ArraySegment<byte>(buffer, read, size - read), SocketFlags.None);
```

### A3. 형식이 깨진 패킷 하나로 서버 전체가 꺼진다

**재현 방법**

1. 서버를 새로 띄운다.
2. LoadTester에서 `4` 를 누른다. Type 필드가 없는 JSON을 보내고, 이어서 정상 채팅 `아직 살아있나요?` 를 보낸다.
3. 서버 창을 본다.

**기대** 그 패킷만 버리고, 다음 채팅은 정상으로 돌려준다.

**실제** 서버 창에 아래 예외가 찍히고 서버가 종료됐다.
```
Unhandled exception. Microsoft.CSharp.RuntimeBinder.RuntimeBinderException:
Cannot convert null to 'int' because it is a non-nullable value type
   at BattleArena.ClientSession.HandlePacket(String json) in …\ClientSession.cs:line 73
   at System.Threading.Tasks.Task.<>c.<ThrowAsync>…
```
LoadTester에는 `→ 전송 실패 : SocketException …` 와 "서버 창을 지금 바로 확인하세요"가 나왔다.

**증거**

- before: `증거/A3_before_malformed_1028_000210.png`, `증거/logs/server_1028_000158.log`
- after: `증거/A3_after_malformed_1028_001850.png`, `증거/logs/server_1028_001821.log`. 서버에 `[경고] ID:1 Type 없는 패킷을 버렸습니다` 가 찍힌 뒤에도 통계 줄이 계속 나왔다. LoadTester는 `{"Type":12,"Nickname":"BadBot","Message":"아직 살아있나요?"}` 를 받았다.

![A3 before](증거/A3_before_malformed_1028_000210.png)
![A3 after](증거/A3_after_malformed_1028_001850.png)

**원인** `OutsourcedServer/ClientSession.cs` L73, L68, L50

- L73: `Type` 이 없으면 `packet.Type` 이 null이고, `(int)null` 에서 예외가 난다.
- L68: `HandlePacket` 이 `async void` 다. 반환하는 Task가 없으니 예외를 담아 둘 곳도, 받아 줄 호출자도 없다. 그래서 예외가 스레드풀로 그대로 던져지고(스택의 `ThrowAsync`) 프로세스 전체가 죽는다.
- L50: `HandlePacket(json);` 을 await 없이 부른다. 그래서 RunAsync를 감싼 try/catch(L43–56)가 이 예외를 잡지 못한다.
- A1의 분할 전송 크래시도 같은 길로 죽었다. 두 스택 모두 `HandlePacket` → `ThrowAsync` 다.

**수업 근거**

- 4주차 19쪽: ClientSession.cs는 "Run() → RunAsync(), 내부 호출도 await".
- 4주차 12–13쪽: Task는 "미래에 완료될 작업"에 대한 접수증이고, 예외가 나면 그 Task가 `Faulted` 상태가 된다. 즉 예외가 Task에 담긴다. `async void` 는 이 Task 자체가 없다.

원본은 10명까지는 전부 성공했고, 50명에서 19명만 성공했다. 10명과 50명 사이 인원은 따로 재지 않았기 때문에, 내가 숫자로 말할 수 있는 건 "10명은 버티고 50명에서 무너진다"까지다. LoadTester의 평균·p95는 성공한 봇만으로 계산한다. 50명에서 성공한 봇의 p95가 9,914ms라서, 성공한 봇도 WELCOME 대기 한도(10초) 직전에 겨우 받은 것이다. 나머지는 10초 안에 WELCOME을 못 받아 실패로 처리됐다. 서버 통계의 접속 수는 계속 늘고 있었으니 접속 자체를 거절한 것은 아니다. 100·300·500명에서도 성공은 22·28·44명에 그쳤다. 사람 수를 10배로 늘려도 성공 수는 두 배 남짓밖에 늘지 않았는데, 이것은 아래 표처럼 서버 스레드가 늘어나는 속도와 비슷하다.

측정 ① 동안의 서버 통계 (`증거/logs/server_1027_233628.log`):

| 서버 t | 접속 | 서버 스레드 | 그때 LoadTester 단계 |
|---|---|---|---|
| 751s | 0 | 12 | 10명 끝 |
| 754s | 14 | 15 | 50명 |
| 762s | 22 | 26 | 50명 |
| 773s | 31 | 32 | 100명 |
| 786s | 41 | 42 | 300명 |
| 800s | 62 | 63 | 500명 |

접속 수와 스레드 수가 거의 똑같이 움직인다. 접속한 사람 한 명이 스레드 하나를 쥐고 있다는 뜻이다. 2초마다 찍혀야 하는 통계 줄도 500명 단계에서는 t=788s 다음이 t=800s로 12초나 벌어졌다. 통계를 찍는 작업도 빈 스레드를 기다렸기 때문이다.

서버를 다시 띄우지 않고 한 번 더 돌린 ①-재에서는 10명에서도 5명이 실패했다 (5/5). 직전 서버 통계는 접속 0, 스레드 3이었다 (t=852s). 왜 10명에서 실패했는지는 따로 확인하지 못했다. B-4에 적은 "로그인 전에 입장 알림이 먼저 가는" 구조 때문일 수도 있다고 생각한다. 조건을 맞추려고 이후 측정 ②·③은 매번 서버를 새로 띄워서 했다. 아래 진행 캡처는 ①-재(23:50 실행) 때 찍은 것이다. 측정 ①의 서버 통계는 위 표처럼 로그에서 옮겼다.

### B-3. 왜 거기서 나빠지나 (코드의 어느 줄 때문인가)

원인 줄: `OutsourcedServer/PacketHelper.cs` L51, L63 `await Task.Run(() => socket.Receive(...))`

| 질문 | 답 (내 숫자로) |

| 내 PC 코어 수는 몇인가 | 12개. 스레드풀이 처음에 바로 내주는 워커 스레드도 12개다 (LoadTester 8번 "스레드풀 최소 : 워커 12") |

| 왜 어느 숫자를 넘으면 갑자기 느려지나 | 묶인 스레드가 최소치 12를 넘으면 남은 일(다음 접속 받기, LOGIN 처리, WELCOME 보내기)이 빈 스레드를 기다리며 줄을 선다. 스레드풀은 그 뒤로 스레드를 천천히만 늘린다. 내 로그에서는 12개에서 63개까지 약 50초, 1초에 하나 정도였다. LoadTester는 WELCOME을 10초까지만 기다리므로 50명 단계부터 대부분이 시간 안에 못 받았다 (p95 9,914ms). 4주차 7쪽에서 배운 "1명당 1쓰레드는 불가능"이 내 PC에서는 12명을 넘는 순간부터 보였다 |
| 고치면 왜 빨라지나 | `socket.ReceiveAsync` 는 기다리는 동안 스레드를 돌려준다 (4주차 11쪽 "쓰레드는 반납한다"). 데이터가 왔을 때만 잠깐 스레드를 빌려 처리하므로 접속자 수와 스레드 수가 따로 논다. 측정 ③에서 `접속 294 / 스레드 12` (서버 t=24s)였고, 스레드는 최고 32개로 500명 중 499명이 성공했다 (`증거/logs/server_1028_002522.log`). 4주차 8쪽 "쓰레드 몇 개로 충분합니다"가 그대로 나왔다 |

② (A1만 고친 측정)은 ①과 거의 같았다. 50명 18/32, 500명 55/445였고 서버 스레드는 최고 83개였다 (`증거/logs/server_1028_002139.log`). 나뉘어 온 패킷을 끝까지 읽게 고쳐도 동시 접속 실패는 그대로였다. 그래서 부하 문제의 원인은 부분 수신이 아니라, 기다리는 동안 스레드를 붙잡는 블로킹 수신이라고 판단했다.

| 6. MAX_BODY 8192는 작다 | 반대 | 8192바이트면 채팅에 충분하다. 서버만 65535로 올리면 TestClient(L257, 8192)가 긴 채팅을 받는 순간 연결이 끊긴다 | 3주차 10쪽 길이 헤더 (길이는 양쪽이 같은 규칙으로 읽어야 한다) |
| 7. Listen(512)는 과하다 | 반대 | 백로그는 Accept를 기다리는 접속 줄의 길이다. 500명이 한꺼번에 붙는 서버인데 100으로 줄이면 몰릴 때 접속이 거절될 수 있다 | 3주차 8쪽 "Listen(100) 동시에 100개까지 대기시킬 수 있음" |
| 8. NoDelay는 대역폭 낭비 | 반대 | 이 서버의 TCP 패킷은 작은 채팅·알림이라 대역폭보다 지연이 더 문제다. Nagle은 작은 패킷을 모으느라 지연을 만든다 | 5주차 5–6쪽: TCP가 기다리는 동작이 "게임에서는 독이 됩니다" (Nagle 자체는 강의자료에 없음) |
| 9. StringBuilder 필드는 위험 | 반대 | `_stateBuilder` 는 브로드캐스트 루프 한 곳에서만 쓰고, Clear → Append → ToString(L154–163) 사이에 await가 없다. 동시에 건드리는 코드가 없으니 섞이지 않는다 | 5주차 16쪽 BroadcastLoopAsync는 루프 하나, 4주차 15쪽 await와 await 사이는 한 조각으로 이어서 실행 |
| 10. 부하 테스트 불필요 | 반대 | 수신이 Task.Run 안의 블로킹 Receive라서 접속자마다 스레드를 하나씩 붙잡는다. 직접 돌려 보니 50명부터 31명이 실패했다 (C-3) | 4주차 16쪽 "흔한 실수", 4주차 4쪽 "신고를 받으면 먼저 재현부터 합니다" |

반대로 판정한 것 중 업체 말이 아주 틀리지는 않은 것도 있어서 따로 적는다.

- 의견 5: 33ms면 약 30.3fps인 것도, Task.Delay가 OS 타이머 영향을 받는 것도 맞다. 하지만 간격이 조금 흔들려도 보간 때문에 화면에서는 차이가 안 난다. 그래서 고정밀 타이머나 보정 루프로 바꿀 이유가 없다고 봤다.
- 의견 6: 8192바이트를 넘는 채팅이 거부되는 것은 맞다. 하지만 상한은 이상한 길이를 막으려고 두는 값이고, 바꾸려면 서버와 클라이언트를 같이 바꿔야 한다.
- 의견 8: NoDelay를 켜면 작은 패킷이 모이지 않고 나가서 패킷 수가 늘 수 있는 것은 맞다. 하지만 채팅·알림 정도의 양에서는 대역폭보다 반응 속도가 중요하다고 판단했다.
